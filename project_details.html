1. Project Overview & Objectives

The DHA Document Management System (DMS) is custom-engineered to solve the physical document tracking and storage challenges faced by DHA offices. In municipal and real estate operations, land records, citizen files, maps, and regulatory notices must be indexed and searched rapidly.

This system establishes a secure digital workflow that moves from scanning physical records to structured database tracking, validator screening, and executive monitoring. By implementing a standardized renaming protocol, it eliminates typographical discrepancies and duplicate records.

Core Project Goals:

  • Role-Based Audited Workflow: Segment responsibilities cleanly among staff who scan/upload, supervisors who validate, and executives who govern.
  • File Standardization: Enforce naming conventions (e.g. DHA-LHR-P1-CNIC-001.pdf) using key metadata tags like Branch, Doc Type, File Number, Phase, Plot, and Doc Year.
  • Security and Integrity: Prevent SQL injection, unauthorized dashboard access, and session hijack attempts.
  • Visual Analytics: Present real-time scan statistics, approval rates, and operator activities to administrators.

3. Role-Based Access Control (RBAC)

To enforce accountability, the system restricts features based on the role_id defined in the database session:

Role Code ID Primary Access Permissions Core Pages Authorized
Admin 1 Full system access. Can create/suspend users, scan, rename, validate, view audit logs, and download reports. All files (users.php, dashboard.php, etc.)
Operator 2 Responsible for digitizing records. Can upload scanned files, input initial metadata, and execute file standardization. scan.php, rename.php, folders.php
Validator 3 Responsible for compliance. Can view pending metadata files, review scanned imagery, and Approve/Validate after Correction with comments. validate.php, folders.php

4. Database Schema Design

The system runs on the dms_database database schema. The design normalizes document metadata, validation records, and logs to ensure performance and relational integrity.

Table: roles
Defines user permission roles.
Column Type Attributes Description
role_id INT PK, Auto Increment Unique ID of the role.
role_name VARCHAR(50) NOT NULL Name of the role (e.g. Admin, Operator).
description VARCHAR(250) NULL Explanation of the role's access boundaries.
Table: users
Stores user account details, encrypted passwords, and status credentials.
Column Type Attributes Description
user_id INT PK, Auto Increment Unique ID of the user.
username VARCHAR(50) NOT NULL, UNIQUE System login handler.
password_hash VARCHAR(255) NOT NULL Encrypted using PHP's password_hash().
role_id INT FK to roles.role_id Determines privileges.
status ENUM 'active', 'inactive', 'suspended' Suspended/inactive users are denied access.
Table: documents
Main index containing metadata, file parameters, and workflow parameters.
Column Type Attributes Description
document_id INT PK, Auto Increment Unique ID of the document.
raw_filename VARCHAR(255) NOT NULL Original filename uploaded.
renamed_filename VARCHAR(255) NULL Standardized name after Operator tagging.
branch, doc_type, file_no VARCHAR(50) NULL Indexing metadata tags.
status ENUM 'pending', 'approved', 'changed' Current state in validation workflow.
folder_id INT FK to folders.folder_id Associated folder grouping.

5. Step-by-Step System Workflow

How a physical document is digitized and processed through the system:

1
Authentication & Access Control (login.php)
Users supply usernames and passwords. The backend performs password_verify(). Active sessions are established with specific roles loaded into $_SESSION['user_role_id']. An audit log entry is written for compliance.
2
Folder Setup (folders.php)
An Operator or Admin creates a logical folder container mapped to a specific physical cabinet or collection (e.g. "DHA Lahore — Phase 1 Records").
3
Scan & Upload (scan.php)
The Operator uploads raw files (PDFs, images) specifying basic data. The files are securely deposited into the uploads/ directory, and initial database documents are written with a pending status.
4
Standardized Renaming (rename.php)
The Operator reviews the raw document, inputs specific tags (Branch, Doc Type, File Number, Phase, Plot, Doc Year), and triggers the standardization. The system generates a clean name (e.g. DHA-LHR-P1-CNIC-001.pdf) and updates the records.
5
Validator Auditing (validate.php)
The Validator reviews the standard filename, metadata fields, and physical image. They submit a decision: Approve (moves status to approved), Validate after Correction (moves status to changed), or Needs Revision. A formal validations record is generated containing audit remarks.
6
Reporting & Monitoring (reports.php & dashboard.php)
Administrators monitor upload metrics, individual operator scan velocities, and approval ratios dynamically using color-coded graphs powered by Chart.js.

6. Comprehensive Viva Q&A Guide

Prepare for your project presentation (Viva) with these potential questions that examiners might ask about your application:

Q1: Which backend language is used, and what is its main role in this project?
Answer: The project uses PHP 8.0+ (specifically configured via MySQLi extension). PHP acts as the server-side logic layer. It parses requests, enforces security sessions using session_start(), filters input parameters to prevent cross-site scripting (XSS), communicates with the database, and processes files uploaded to the filesystem.
Q2: How are user passwords secured? If I inspect the database, will I see plain passwords?
Answer: Passwords are not saved in plain text. They are securely encrypted using the industry-standard Blowfish hashing algorithm (bcrypt) via PHP's built-in password_hash($password, PASSWORD_DEFAULT) function. When a user logs in, the system compares the input password against this database hash using password_verify(), protecting the credentials from exposure if the database is compromised.
Q3: How does the system restrict a standard Operator from accessing Admin pages like User Management?
Answer: The system enforces Role-Based Access Control (RBAC). Upon login, the user's role ID is stored in $_SESSION['user_role_id']. On protected pages like users.php, there is an absolute check: if (getUserRoleId() != 1) { header('Location: ../dashboard.php?msg=unauthorized'); exit(); }. This terminates execution immediately for non-admin accounts.
Q4: What is the purpose of the activity_log table, and how does it get populated?
Answer: The activity_log table tracks system modifications for accountability. It is populated by the global helper function logActivity($conn, $userId, $actionType, $description). Whenever an action occurs (e.g. login, folder creation, doc upload, renaming, validator approvals), this function inserts a log entry linking to the executing user and targets.
Q5: Explain the connection configuration. What port does MySQL use here?
Answer: The configuration is centralized in includes/config.php. It connects to the MySQL server on host 127.0.0.1 using port 3307, configured dynamically using PHP's native new mysqli(). Centralized connection variables prevent code redundancy and allow easy deployment changes.
Q6: How does the document renaming step prevent database duplicates?
Answer: In rename.php, the Operator specifies clean metadata (Branch, Type, File Number, Phase, Plot, Year). The server-side script merges these tags into a structured, unified naming format. This standardization is updated in the renamed_filename field of the documents table, ensuring uniform nomenclature.
Q7: What steps are taken in the code to sanitize input variables?
Answer: In includes/config.php, custom functions are defined: clean() uses trim() and strip_tags() to strip HTML code tags, preventing Cross-Site Scripting (XSS). Additionally, the system uses prepared queries ($conn->prepare() and bind_param()) to guarantee parameters are treated as literal values, completely neutralizing SQL Injection attacks.
